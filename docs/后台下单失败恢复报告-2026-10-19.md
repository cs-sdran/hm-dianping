# 后台下单失败恢复报告

日期：2026-10-19。

## 已完成的处理

后台下单抛异常后，会保存原订单号、用户 ID、优惠券 ID、执行次数和原因，并延迟重试。最多执行 3 次，包含第一次执行和两次重试；重试分别等待 1 秒、2 秒，由独立调度线程执行，不占住新订单的消费线程。

失败任务保存在 Redis Hash `seckill:failed:orders`，字段是订单号，值为 JSON：

- `RETRY_PENDING`：当前应用已安排重试。
- `MANUAL_REVIEW`：执行次数耗尽、业务返回失败或重试调度已停止，需要进一步核对。

重试始终使用原订单号。事务下单方法会先按订单号查订单；若已存在且用户、优惠券都匹配，直接返回原订单号，不再扣库存或插入。订单号匹配但用户或优惠券不匹配时会报错。

成功后删除对应失败记录。删除失败只记日志，不把已成功订单变成失败，也不执行库存回补。业务失败保留待核对记录，不自动释放购买资格。

涉及文件：

- `VoucherOrderAsyncService.java`：有限重试、失败记录、成功清理、关闭调度线程。
- `VoucherOrderTxService.java`：相同订单号重复执行的校验和返回。
- `RedisConstants.java`：失败记录 Hash 的 key。

## 修复前的问题已真实复现

在独立 MySQL 测试库中创建初始库存为 3 的新券，仅对其订单 INSERT 添加拒绝触发器。

请求返回受理成功后，后台确实执行了扣库存和订单 INSERT，INSERT 被拒绝，数据库事务回滚。此时 MySQL 库存为 3、订单数为 0；Redis 库存为 2，用户仍在购买集合中。

解除数据库故障后，同一用户切换应用实例重试仍提示“买过了”。另一个用户可以正常下单，证明消费者仍在运行，但之前失败的任务没有被恢复。

旧实验一度因 Windows 中文日志编码而误判超时；脚本已改为只检查英文故障标记、ERROR 和类名。修复前实验的完整结果为 `RECOVERY_GAP_REPRODUCED`，不是功能通过。

## 修复后的真实故障联调

使用两个真实应用 JVM、独立 Redis、独立 MySQL。通过真实 HTTP 创建新券并发起秒杀。

| 场景 | 实际结果 |
| --- | --- |
| 库存 3，首次后台 INSERT 被拒绝 | MySQL 回滚至库存 3、订单数 0，Redis 保留预扣库存 2，并写入待重试记录 |
| 解除故障，不重新提交购买请求 | 后台自动使用原订单号 `1432032290799617` 完成订单；MySQL 与 Redis 库存均为 2，仅一张订单 |
| 重试成功后的失败记录 | 对应 Hash 字段被清理 |
| 同一用户跨 JVM 再买 | 被重复购买检查拦截，库存保持 2 |
| 另一用户继续购买 | 正常落单，两边库存均为 1，累计 2 单 |
| 另一张券持续拒绝 INSERT | 总共执行 3 次后停止；保留准确的订单、用户、优惠券和异常原因，状态为 MANUAL_REVIEW |

持续故障的测试券初始库存为 2，最终 MySQL 库存 2、订单数 0；Redis 库存 1，仍保留该用户的预扣。该任务需要人工核对或后续恢复流程，不会凭空报告购买成功或无条件释放库存。

故障注入触发器在实验结束前已删除。故障日志中的 4 次 ERROR 属于预期注入：一次临时故障，以及另一张券连续 3 次故障。

## 尚未覆盖的能力

当前订单队列和延迟重试仍在应用内存中。失败记录留在可用的 Redis 中，但程序启动时尚不会自动重放这些记录，也没有人工处理接口；尚不能保证宕机恢复。Redis 同时不可用时，会尝试本进程的有限重试并记录完整任务日志，无法保证失败记录写入 Redis。

本次没有实现永久失败后的自动库存补偿。后续需要可靠任务交付、订单状态查询与核对恢复；补偿前必须确认订单和本轮预扣的归属，不能仅凭一次异常无条件加库存。
