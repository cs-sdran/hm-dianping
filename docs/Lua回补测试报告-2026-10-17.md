## 新增测试结果

| 场景 | 实际通过的断言 |
| --- | --- |
| 正常预扣后回补 | 库存 5 → 4 → 5，返回 0，用户记录删除 |
| 回补后立即再次回补，期间没有新的预扣 | 第二次返回 1，库存保持 5 |
| 有库存但没有用户记录 | 返回 1，库存不增加，不创建购买记录 |
| 库存和用户记录都不存在 | 返回 1，不创建任何 key |
| 有用户记录，但库存 key 缺失 | 返回 5，不重建库存，用户记录保留 |
| 回补另一个没有预扣的用户 | 返回 1，原用户记录和库存保持原样 |
| 同一用户预扣了两张券，只回补其中一张 | 仅指定优惠券恢复库存、删除记录，另一张不变 |
| 回补后该用户重新申请资格 | 新预扣返回 0，库存再次扣减，用户重新记入集合 |
| 预扣后库存被改为 `abc` 或 `1.5`（2 项） | INCR 执行失败，Java 抛出数据访问异常，原库存值和用户记录均保留 |
| 同一轮预扣之后并发回补 50 次，期间没有新的预扣 | 1 次返回 0、49 次返回 1，库存仅恢复一份，用户记录删除 |

并发测试使用同一测试 JVM 内的 20 个工作线程执行 50 个调用，交替使用两个真实 Redis 客户端。

## 结论与适用范围

之前的两个 Lua 返回类型判断问题已修正，现有回补操作在上述场景中符合预期。

当前用途仍限定为：预扣成功后，队列 offer 明确返回 false，任务从未入队，立即撤销本次预扣。没有测试秒杀 HTTP 入口、入队失败后的整体调用链、后台落单或数据库事务。

非整数库存属于异常路径，当前行为是抛异常并保留现场，不是返回 5 或自动修复库存；调用方仍需处理这种异常。

当前购买集合仅保存用户 ID，不能识别不同轮次的预扣。测试中的重复回补保证只覆盖“同一轮预扣、期间没有新预扣”的情况。不能把这个方法直接视为支持任意延迟重试的通用补偿，也不能在任务已经入队或订单已创建时直接调用它。
