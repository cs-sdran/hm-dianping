# 秒杀入口已接入 RabbitMQ

原来的 `VoucherOrderServiceImpl` 在 Redis 校验通过后把订单放进本进程的阻塞队列。现在改为调用 `SeckillOrderPublisher`，发送 JSON 订单消息到 RabbitMQ，由已有的 `SeckillOrderConsumer` 调用事务服务创建订单。

```mermaid
flowchart LR
    A[秒杀请求] --> B[活动时间与分布式锁]
    B --> C[Redis Lua 校验并预扣]
    C --> D[保存发送待核对记录]
    D --> E[RabbitMQ 发布与确认]
    E --> F[队列中的订单消息]
    F --> G[消费者调用事务服务]
    G --> H[扣数据库库存并保存订单]
```

## 这次修改的职责

1. `VoucherOrderServiceImpl` 负责资格预扣、调用发布服务，以及根据发送结果返回响应或恢复预扣。
2. 新增 `SeckillOrderPublisher`，负责组装 `orderId/userId/seckillId`、设置持久化消息、关联发送确认、保存及清理待核对记录。
3. `SeckillOrderConsumer` 继续沿用原订单号调用事务服务，原有的有限重试和死信处理保留。
4. `VoucherOrderAsyncService` 保留作学习对照，移除了 `@Service`，不再随应用启动内存队列消费线程。

## 为什么要区分发送结果

| 发布结果 | 入口响应 | Redis 预扣 |
| --- | --- | --- |
| 收到 ACK，且没有退回消息 | success=true，data 为字符串订单号，表示已受理 | 保留 |
| 发送前待核对记录写入失败，本次没有发送 | 提示稍后重试 | 尝试恢复 |
| Broker 明确退回无路由消息 | 提示稍后重试 | 尝试恢复 |
| 发送异常、确认超时、等待被中断、NACK | success=false，提示结果确认中，data 保留原字符串订单号 | 保留，等待核对 |

恢复预扣失败时返回“预扣恢复异常”，保留记录及日志供核对。确认成功后的记录清理失败不会把已受理订单改成发送失败。

发布确认表示 Broker 已接收消息，不代表数据库订单已经创建；发布确认与消费者确认是两个独立环节，见 [RabbitMQ 确认机制](https://www.rabbitmq.com/docs/confirms)。

仅检查 ACK 也不够：无路由消息仍可能收到 ACK，因此同时启用了 mandatory 退回检测。Spring AMQP 的 CorrelationData 会在确认 Future 完成前填入退回消息，见 [CorrelationData 文档](https://docs.spring.io/spring-amqp/docs/2.2.20.RELEASE/api/org/springframework/amqp/rabbit/connection/CorrelationData.html)。实现使用项目实际依赖的 2.2.18 API，并已通过真实 Broker 退回测试。

## 本地连接配置

已在现有 application.yaml 的 spring.rabbitmq 下补充以下非敏感配置：

```yaml
publisher-confirm-type: correlated
publisher-returns: true
template:
  mandatory: true
```

消息声明为持久化，交换机、业务队列和死信队列继续使用持久化声明。发送确认最长等待 5 秒；数据库写入不在请求线程内执行。

本地 application.yaml 被 Git 忽略，连接凭据没有写进本说明；迁移运行环境时需要同步上述发布配置和现有消费者重试配置。

## 待核对记录

Redis Hash：`seckill:publish:pending`。字段为订单号，值保存订单号、用户 ID、优惠券 ID、状态、原因及更新时间。

- `PUBLISH_PENDING`：发送前已保存。也可能是已发送成功但清理失败，需查订单后判断。
- `PUBLISH_RETURNED`：Broker 明确退回。入口恢复预扣成功后清除该记录。
- `PUBLISH_UNKNOWN`：发送结果不确定。保留预扣，避免消息实际已到达时重复释放购买资格。

这些记录没有自动过期，也没有自动补发线程。核对时需同时查看数据库订单和队列/死信；若需补发，必须沿用原订单号，不能生成新订单号或直接释放库存。本次增加的是可核对的发送记录，Redis 预扣与记录写入尚未组成一个原子操作，也未实现自动对账恢复。
